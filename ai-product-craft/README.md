# 可验证的 AI 产品开发：研究与候选 v0.1

目标是让 AI 交付能够逐条检验的产品，并将真实返工变成可复用的开发知识。当前是研究和可运行候选，不是经过真实产品长期验证的成品。项目暂名 `ai-product-craft`，候选 Skill 名为 `evidence-driven-delivery`。

## 从这里学习

1. [研究结论](research/FINDINGS.md)：下载了什么、学什么、舍弃什么，以及证据边界。
2. [候选 Skill](skill/SKILL.md)：从用户承诺到验收和返工的完整主线。
3. [机制与来源](skill/references/mechanisms.md)：每条规则改变什么决定，来自哪里，有什么反例。
4. [工具与运行](skill/references/tooling.md)：执行检查、证据失效判定、返工经验存储。
5. [验证结果](evals/RESULTS.md)：工具测试与独立对照的原始结论。

## 本地运行

Python 3.11+，自写工具仅使用标准库。在本目录运行：

```powershell
python -m unittest discover -s tests -v
python skill/scripts/delivery.py --help
```

在业务项目中使用时，先按 `skill/references/tooling.md` 写该项目真实的验收合同，再指定项目根目录执行工具。命令不是沙箱；不要把生产写入命令或凭证放入合同。全局目录未安装本候选，也未改动已有产品/前端/ub-mode Skill。

## 自进化做到哪一步

已实现：项目内的返工记录、相关经验检索、证据关联和完整性检查、替代旧经验、候选规则提案。

未实现：后台自动监听所有聊天、自动训练模型、自动修改全局 Skill、跨工具无条件捕获、自动建立 CI、自动发布。开启一个采用本 Skill 的开发会话后，由 Agent 按触发条件实际调用记录工具。自动记录的可靠性仍需要项目实战验证。用户明确指出的纠正是信号；真正学到什么还需要证据与适用条件。

## 舟序实战

已在真实前后端项目开展第一轮验证，见[方法v2验收](../docs/acceptance/method-v2/README.md)及[Huashu七仓库研究](research/huashu-20261105/FINDINGS.md)。保留独立盲比较的负面发现：结构化交付已连通，证据事实推理仍未全部通过，不宣称候选普遍优于旧方法。

## 下一阶段

选择一个真实的前后端业务切片，冻结用户承诺与验收标准，比较现有工作流和候选。衡量真实漏验、返工次数、首次有效交付时间、误报和额外耗时。通过后再考虑全局安装、跨项目规则和公开发布。对真实项目的永久规则修改应展示可审阅差异并由用户批准。
