# Maritime field case: distinguish decisions, not introductions

The first maritime catalog repeated one runtime-policy paragraph across eight skills and added one short specialist paragraph to each. The UI displayed the repeated paragraph first. Although the model, corpus, accounts and cases worked, the user correctly found the skills difficult to distinguish and the UI explanatory copy intrusive.

The project response changed three different things:

1. Presentation: show inputs, specialist steps, actual deliverables and useful starting examples. Keep operational policy in the server-resolved context; preserve the user's explicit copy preferences.
2. Mechanism: a law applicability table, case comparison matrix, clause revision sheet, competing case hypotheses, evidence timeline, decimal claim ledger, draft sections and dependency-aware handoff are different work products. Their fields must support the actual next user's action.
3. Verification: store work products on a trusted run, enforce account access, check columns and citations, and recompute claim amounts. A saved artifact is evidence of that persistence operation, not proof its legal analysis is correct.

Study sources were pinned versions of seven Huashu skill-related repositories, with MIT notices and a repository-level research ledger. Only mechanisms were adapted: demand routing, failure branches, domain-specific artifacts, paired evaluation and project-local learning. Persona impersonation, unconditional approval rituals, automatic commits and absolute self-scores were not adopted.

Actual paired observations matter more than that design explanation. In the first four-case comparison, both old and new business instructions could produce saved work packages under the same new runtime/tool contracts. Independent label-hidden review preferred the candidate for the contract task, preferred the old method for the evidence task, and found the claim and short-answer cases comparable. Both evidence outputs still conflated dates of different events in places. This led to a narrower correction: identify the event before comparing dates, distinguish inspection/completion from request receipt, then test a separate shipment/issue/notice scenario. Do not describe the first run as a general candidate win.

Another real failure occurred when a strict work-package tool rejected an extra table but returned a metadata schema as its repair hint. The model then submitted that metadata as a data row. The fix was an actionable input example and row-value schema, while preserving the actual data checks. A code boundary review also found that tool and API independently chose persistence paths; one shared configured-store factory fixed the saved-but-invisible result.

The project keeps raw outputs, negative runs and the reviewer reports. Small samples support observations under the tested conditions; they do not establish year-long professional experience, legal correctness, expected Star growth or statistical stability. Follow-up claims must cite the corresponding project evidence rather than repeating this story as a universal rule.
