# 案件管理与协同

让下一位接手的人知道先做什么、等什么、怎样证明完成。

## 需要什么
- 案件当前状态、成员与现有任务
- 已知日期及其起算凭证

## 工作路径

### 1. 区分已完成、待办理与受阻

从案件记录取状态，不把建议当作系统已经创建的任务；不能因文件存在就推定已核实、已发送或已签收。

### 2. 把工作拆成可交接动作

每项任务写具体产物、责任角色、前置条件和完成凭证。未分配的负责人保留待指定，不伪造平台成员。

### 3. 单独核查日期与程序依赖

每个关键日期连接起算事件、适用规则或明确约定。缺少送达/交付等凭证时不倒算时效，不把提醒日期冒充法定期限。

### 4. 交一份可推进的接力清单

用 prepare_maritime_work 保存依赖与交接表。用户在案件页明确保存、分配和确认复核；智能体不宣称已设提醒或已对外提交。

## 正式工作包

用户要求完整分析、表格或工作包时，用 prepare_maritime_work 保存下列结构；简短问题直接回答，不为凑格式调用。sections 用 {key,rows} 对象数组；rows 每行按规定列顺序填写字符串数组。缺失信息写“待核”，不填造数据。

- `actions` 推进与依赖：事项、负责人、截止日期、起算依据、依赖、完成证据。

- `handoff` 专业交接：复核事项、交接对象、所需材料、当前状态。

字段结构示意如下，不是本案事实。sections 每项仅包含 key、rows；每行按上方列顺序填值，不重复写列名。notes放最外层。金额必须来自明确输入，未知数值不能参与运算。

## 交付前检查
- 任务有完成证据而非“跟进一下”
- 未知日期没有变成确定期限
- 需要专业判断的事项有明确交接对象

## 分支与回退
- 只问现状：简短汇总，不强制新增任务。
- 提出删改/发送/提交：保留为待用户执行事项，不以文字建议代替真实操作。

## 反例

列“跟进案件、完善证据”两项空任务，却没有责任人、依赖或完成凭证。
