# 案例检索与分析

把“有相似案例”推进到“为什么可比、哪里不能照搬”。

## 需要什么
- 本案的关键事实和争点
- 希望支持或检验的主张；没有预设立场也可

## 工作路径

### 1. 提取真正可比的事实

从争点反推检索条件：单证流转、持单身份、交付方式、损害原因、程序阶段。不要只用“货损”一个主题词判断相似。

### 2. 找支持案例，也找不利案例

调用 cases 检索；优先保留裁判理由与关键事实完整的片段。支持不足可减少案例数量，不为凑数列不相关案例。

### 3. 做差异对照

把裁判结论放在其事实和程序背景下，与本案逐项比较。事实相像但法律关系、举证状态或适用版本不同，应说明该差异可能改变什么。

### 4. 交可使用的比较结论

给出最值得读的案例及不宜援引的理由，调用 prepare_maritime_work 保存比较矩阵。只拿到片段不能声称通读判决。

## 正式工作包

用户要求完整分析、表格或工作包时，用 prepare_maritime_work 保存下列结构；简短问题直接回答，不为凑格式调用。sections 用 {key,rows} 对象数组；rows 每行按规定列顺序填写字符串数组。缺失信息写“待核”，不填造数据。

- `comparisons` 类案差异矩阵：案例、关键事实、裁判理由、相似点、决定性差异、依据。

- `implications` 对本案的启示：拟用观点、可比前提、不能照搬之处、下一步核实。

字段结构示意如下，不是本案事实。sections 每项仅包含 key、rows；每行按上方列顺序填值，不重复写列名。notes放最外层。金额必须来自明确输入，未知数值不能参与运算。

```json
{
  "skill_id": "case-research",
  "title": "本次工作标题",
  "sections": [
    {
      "key": "comparisons",
      "rows": [
        [
          "待核",
          "待核",
          "待核",
          "待核",
          "待核",
          "待核"
        ]
      ]
    },
    {
      "key": "implications",
      "rows": [
        [
          "待核",
          "待核",
          "待核",
          "待核"
        ]
      ]
    }
  ],
  "notes": []
}
```

## 交付前检查
- 案例标题和引用来自实际命中，不向用户输出数据库内部编号
- 每案有决定性差异而非笼统相似度
- 未把案例见解写成普遍必然规则

## 分支与回退
- 没有本案事实：先做主题案例地图，把比较前提留空。
- 命中只有摘要：标明理由缺失，不能推断全部裁判要旨。

## 反例

给三个案件贴“高度相似”标签，不交代不同事实如何改变结果。
