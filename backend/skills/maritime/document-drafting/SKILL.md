# 文书起草

交一份可以继续编辑、核对和签发的文书草稿。

## 需要什么
- 文书类型、收件对象与希望推动的动作
- 已确认事实、依据和必须保留的表达

## 工作路径

### 1. 先确定这份文书要推动什么

区分保留权利通知、谈判索赔函、内部法律意见和诉讼/仲裁草稿。读者与目的决定结构，不能一律套律师函口吻。

### 2. 给事实建立出处

将确认事实、对方主张、推断和诉求分开。依据只引用实际材料或检索结果，不把草稿中的表述反过来当事实。

### 3. 写可以直接编辑的正文

缺少姓名、日期、单号、金额时用清楚占位符；不因可占位字段缺失而拒写整份草稿。未经确认的事故原因不写成对方已承认。

### 4. 做签发前核对

用 prepare_maritime_work 保存正文和补齐清单。检查收件人、事实表述、附件、金额、版本和发出权限；保存草稿不表示已发送或已提交。

## 正式工作包

用户要求完整分析、表格或工作包时，用 prepare_maritime_work 保存下列结构；简短问题直接回答，不为凑格式调用。sections 用 {key,rows} 对象数组；rows 每行按规定列顺序填写字符串数组。缺失信息写“待核”，不填造数据。

- `document` 可编辑正文：段落、正文、事实或条款依据。

- `placeholders` 签发前补齐：字段、待补内容、影响。

字段结构示意如下，不是本案事实。sections 每项仅包含 key、rows；每行按上方列顺序填值，不重复写列名。notes放最外层。金额必须来自明确输入，未知数值不能参与运算。

```json
{
  "skill_id": "document-drafting",
  "title": "本次工作标题",
  "sections": [
    {
      "key": "document",
      "rows": [
        [
          "待核",
          "待核",
          "待核"
        ]
      ]
    },
    {
      "key": "placeholders",
      "rows": [
        [
          "待核",
          "待核",
          "待核"
        ]
      ]
    }
  ],
  "notes": []
}
```

## 交付前检查
- 正文与待补字段能相互对应
- 目的与语气匹配
- 没有编造材料编号、承诺或已送达状态

## 分支与回退
- 只要一封短邮件：直接交正文，不强迫复杂文书结构。
- 关键诉讼资格或请求基础缺失：交可用草稿范围，同时指出会改变请求的事实。

## 反例

为了让文书看起来完整，编造提单号、损失金额或对方承认。
