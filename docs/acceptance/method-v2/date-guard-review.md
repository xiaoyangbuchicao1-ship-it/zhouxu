## 日期守卫边界

最初前缀匹配版本会把“2026年10月8日之前（具体日期未知）”当作固定10月8日，继而拒绝下一行10月7日。我独立复现并报告过这项误拒绝；其实际日期可能早于10月7日，不能据上界推断倒序。

当前改为整个时间单元格fullmatch完整ISO或中文单日。本轮独立重测：

| 输入 | 结果 |
|---|---|
| 10月8日之前（具体未知）→完整10月7日 | 接受，不取截止日前缀当确定日期 |
| 完整2026-10-08→日期未知→完整2026年10月7日 | 拒绝倒序 |
| 完整10月7日→未知→完整10月8日 | 接受，未知保持原样 |
| 2026-02-30 | 拒绝无效日历日期 |
| 完整10月8日→10月7日（甲方主张） | 接受，括注日期不纳入守卫 |

因此误拒绝在当前声明的精确单日边界下已修复。最后一行也说明：这不是所有自然语言日期检查器，带主体括注的明确日期仍不比较，不能声称其会阻止所有样本式倒序。代码不改日期、不自动移行、不判断事件真假。checks.complete_date_order=checked_when_parseable仅代表此有限范围。

## 保留的具体负面

- evidence A把卸货发现受潮之前的检验直接称为先后冲突，仍缺检验对象、地点和范围的对应证据。保存gaps更把实际检验日限制为“10月7日还是10月9日之后”，10月9日只是乙方收件主张，不能用作实际检验日期的另一个候选下界。问题进入持久化表格。
- evidence A保存来源仍称装卸货文字为“原始记录”，但fixture只提供演示文本，并未说明原件/复印件形式，不宜升级证据形式。
- evidence B第3段明载的日期被标未知，不是守卫“保留未知”的成功：它本来不是未知。表内重复拆开后日期子序列虽有序，整体仍不忠于原文关联。
- evidence B虽开头说三个事件不同，随即又以“请求应在检验前或当日发出、乙方两日后收到”为难以并存的理由。这仍把发送与收到的间隔当作矛盾，没有发送凭证、参与人或送达耗时依据。
- evidence B初行未知位于已知日期之前。当前守卫仅检查可解析日期的子序列，因此不会检测未知行布局、重复事件或已知日期被抹去，不能把检查通过理解为完整时间线质量合格。
